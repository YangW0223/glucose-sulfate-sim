# 葡萄糖中硫酸盐检查 Web 3D 高拟真实验——开发提示词

> 用途：作为 Codex / Claude Code / Cursor Agent 等编码代理的项目总提示词。
> 目标：固定实验操作台 + 自由操作 + 高拟真 + 操作结果由真实状态计算产生，而不是“点击下一步播放预设动画”。

你是一名资深 Web 3D 仿真系统架构师、Three.js 工程师、物理仿真工程师。

现在需要开发一个“葡萄糖中硫酸盐检查”Web 3D 高拟真实验。

我会提供：
1. 《葡萄糖中硫酸盐的检查.docx》
2. 参考实验视频
3. 当前前端项目代码（如果存在）

请以我提供的实验文档作为实验需求的主要依据，以参考视频作为视觉表现、镜头、动作方式的参考。

注意：
这不是一个“点击下一步播放动画”的教学页面，也不是简单的 3D 展示页面。

我要实现的是：

“固定实验操作台场景下，可以自由拿取、移动、放置、旋转、倾倒、量取、吸液、混匀、观察，并且操作结果由实际操作数据决定的 Web 3D 高拟真实验。”

## 一、核心产品目标

整个实验必须始终发生在一个真实的 3D 实验操作台环境中。

用户进入实验后，应当看到：

上方：实验仪器和试剂存放区域。
中央：3D 实验操作台。
右侧：药典正文 / 当前实验说明。
下方：实验步骤提示、操作提示等 UI。

但是“步骤提示”只负责教学引导。

不能出现：

点击“下一步”
→ 自动移动仪器
→ 自动倒液
→ 自动播放实验动画
→ 自动得到结果

实验操作必须由用户自己完成。

例如：

用户必须自己拿起量筒；
自己移动到比色管附近；
自己倾斜量筒；
系统根据量筒的真实姿态计算液体是否流出；
根据持续时间计算流出了多少；
根据液流落点判断液体进入比色管还是洒到实验台；
最终比色管实际增加多少液体，由仿真结果决定。

优先使用：

- React

- Three.js
- @react-three/fiber
- @react-three/drei
- @react-three/rapier / Rapier
- Zustand
- GSAP
- GLTF / GLB

必要时可以评估 WebGPU，但不要为了 WebGPU 增加不必要复杂度。

架构必须保证以后可以增加：氯化物检查、铁盐检查、重金属检查、澄清度检查和其他药学 / 化学虚拟实验。

不能把所有逻辑写死在当前实验组件中。

## 三、最重要的架构原则

整个系统至少拆成：

1. Rendering System
2. Physics System
3. Interaction System
4. Instrument System
5. Container System
6. Liquid System
7. Substance System
8. Reaction System
9. Experiment Rule System
10. Simulation State
11. UI System

3D 模型只负责表现。

不能让 `NesslerTube.tsx` 直接知道“我现在正在做葡萄糖硫酸盐检查第 5 步”。

比色管只应该知道自己的物理属性：容量、尺寸、当前液体、当前位置、姿态、能否被拿起、开口位置、碰撞体、液体状态。

具体实验规则由 Experiment Engine + Experiment Rules 控制。

## 四、实验操作台

实验台不是一个背景模型，而是整个仿真的真实世界空间。

建议统一使用真实世界单位：`1 Three.js unit ≈ 1 meter`。

例如实验台：宽约 2.4m、深约 1.2m、高约 0.85m。具体尺寸可以根据视觉效果调整，但是整个系统必须统一尺度。

所有仪器的 position / rotation / scale / 碰撞 / 距离 / 液流 / 重力都必须在同一世界坐标系中计算。

实验台设置固定碰撞体：`RigidBody type="fixed"`。

实验仪器正常状态为 Dynamic Rigidbody；用户拿起物体时切换为 KinematicPositionBased；松开之后重新切换为 Dynamic Rigidbody。

## 五、仪器拿取系统

不能使用 HTML drag & drop。

必须使用 Pointer Events + Raycaster + 3D World Coordinate + Rapier。

完整流程：

鼠标按下
→ Raycast 命中仪器
→ 仪器进入 HELD 状态
→ 转换为 Kinematic Rigidbody
→ 鼠标移动
→ 根据鼠标射线与操作平面计算目标位置
→ 仪器实时跟随
→ 松开
→ 恢复 Dynamic Rigidbody
→ 重力和碰撞开始生效

仪器状态至少包括：SHELF / ON_TABLE / HELD / OPERATING / FALLEN。

不要简单写成 `isDragging: boolean`，要设计成完整对象状态系统。

## 六、每件仪器都必须定义真实语义

例如纳氏比色管：

- capacity = 50ml
- markings = [25ml, 50ml]
- innerRadius
- innerHeight
- mouthPosition
- bottomPosition
- currentVolume
- contents
- turbidity
- temperature
- mixedState

模型本身最好提供 Anchor Points，例如：Glass / LiquidVolume / Scale / Label / Cap / Anchors(Mouth, Bottom, GrabPoint, PourPoint, PipettePoint)。

Anchor 可以在 Blender 中使用 Empty 制作，加载 GLB 后读取这些节点。

## 七、液体系统

禁止仅通过 `liquid.scale.y = volume / maxVolume` 模拟所有液体行为。

液体必须拥有真实状态：volume、density、viscosity、color、transparency、turbidity、substances。

液面必须受到世界重力方向影响。容器倾斜以后，液面不能跟随容器一起倾斜，应保持接近世界坐标水平面。

需要研究并实现：World Space Liquid Plane + Container Local Space + Clipping / Shader。

液面高度由容器几何 + 当前液体体积共同决定。

## 八、真实倾倒系统

禁止：拖到目标附近 → 自动播放 pour animation → 自动加入 40ml。

必须实时计算。

每帧获得：容器世界姿态、瓶口世界位置、液面位置、剩余体积、容器倾斜角、液体粘度。

当液面达到瓶口以后才允许产生液流。

设计 `calculatePourRate({ geometry, rotation, volume, viscosity, gravity })` 得到 ml/s。

每帧：`source.volume -= flowRate * deltaTime`。

液流受到重力影响，判断液流轨迹是否穿过目标容器开口。命中则增加目标体积，否则落到实验台。

必须支持：倒准、倒偏、倒洒、少倒、多倒。

系统不能偷偷把 37.8 ml 修正成 40 ml。

## 九、实验台洒液

WorkbenchState 应支持 `spills: Spill[]`。

液体倒到桌面以后产生视觉洒液区域，第一阶段可以使用 Decal / Plane / Shader 模拟；暂时不需要完整流体铺展，但数据层必须真实记录洒了什么、洒了多少、洒在哪里。

## 十、量筒和液体读数

用户应该能通过真实刻度观察液面，而不是永远在旁边显示 40ml。

支持摄像机靠近 50ml 量筒、10ml 量筒、刻度吸管、比色管。

液体表面应表现基本弯月面；对于水溶液表现为凹形弯月面。

教学模式可以提供辅助提示，考核模式下不要直接告诉用户“当前为 40.00ml”。

## 十一、称量系统

葡萄糖称量不能设计为“点击一次 +0.2g”。

需要完整称量流程：拿称量纸 → 放到电子天平 → 显示称量纸质量 → 去皮 → 归零 → 拿药勺 → 取葡萄糖 → 移到称量纸上方 → 倾斜 → 葡萄糖逐渐落下 → 天平质量实时变化。

数据必须真实记录 paperMass / tareMass / glucoseMass / displayMass。

正确区间按照实验文档：1.95g ～ 2.05g。

系统不要自动把数据吸附成 2.00g。

## 十二、粉末系统

第一版本无需真正模拟数万个葡萄糖颗粒，但必须从数据上保持真实。

药勺存在 powderMass；当药勺倾斜超过阈值以后，根据倾斜角、剩余粉末、时间计算 powderFlowRate。

视觉效果可以使用 Particle System 表现粉末下落。

## 十三、刻度吸管

本实验使用 5ml 刻度吸管。

需要支持：插入标准硫酸钾容量瓶、使用洗耳球产生吸力、吸取液体、液面上升、调整至目标刻度、移动吸管、向对照管放液。

不要“点击吸管 → 自动得到 2ml”。

用户必须感受到吸得过快、吸过刻度、吸得不足、放液过多、放液不足。

## 十四、化学物质系统

不要只保存 liquidColor，必须保存真实成分。

需要支持：标准硫酸钾、稀盐酸、25%氯化钡、葡萄糖、水、硫酸根、硫酸钡沉淀。

## 十五、Reaction Engine

实验结果不能根据 `currentStep === 6` 直接修改浑浊度。

需要建立 Reaction Engine。当含 SO4²⁻ 的体系加入 Ba²⁺ 后产生 BaSO4 沉淀。

第一版本不要求构建完整通用化学模拟器，但必须建立可扩展的数据模型：reactants / products / stoichiometry / conditions。

Reaction Engine 根据当前成分、加入体积、浓度、反应条件计算生成物量；precipitateAmount 进一步影响 turbidity；最终 Shader 根据 turbidity 渲染透明、轻微灰蒙、明显浑浊。

## 十六、混匀

用户必须自己拿起比色管完成混匀。

系统监控 rotation / angularVelocity / shakeAmplitude / shakeCount。

前面的混匀要求：以管口为支点，左右轻微摆动，角度不超过约 5°，连续约 3 次。

不要点击“混匀”然后自动播放动画。

## 十七、静置

静置必须基于真实 Simulation State。

教学模式下可以将 10min 实验时间映射为约 5 秒展示时间，但系统内部要明确区分 physicalExperimentTime 与 simulationDisplayTime。

## 十八、最终观察

允许为了观察效果将摄像机移动到两支纳氏比色管上方，并切换黑色背景、自上而下观察。

不要直接显示固定结果图片。

最终浑浊程度必须来源于真实称样量、标准液实际体积、水体积、盐酸体积、BaCl2 实际体积、混匀程度、静置时间、反应生成物、浑浊度。

前面操作发生变化，最终观察结果必须发生变化。

## 十九、玻璃材质

大量使用玻璃仪器，必须重点优化玻璃视觉效果。

至少考虑 MeshPhysicalMaterial / transmission / IOR / roughness / thickness / environment map。

玻璃必须有真实厚度、边缘反射、高光、透明感、液体与玻璃界面的视觉差异，不能只是 `opacity: 0.3`。

同时，为教学可读性，玻璃不能透明到“看不见”；需要通过边缘高光、轻微吸收色、Fresnel、clearcoat 和背景对比保证识别度。

## 二十、摄像机

不需要第一人称在实验室走动。

主要围绕实验操作台，采用半固定实验视角 + Orbit + Zoom + 操作聚焦。

限制 Orbit 范围；读取量筒、吸管、天平时允许放大观察，但不要强制自动切换所有镜头。

## 二十一、实验流程

根据提供的实验文档完成流程：

两支 50ml 纳氏比色管：左侧供试管、右侧对照管。

供试管：称取约 2.0g 葡萄糖 → 放入供试管 → 加水溶解约至 40ml。

对照管：使用 5ml 刻度吸管量取标准硫酸钾溶液 → 加入对照管 → 加水约至 40ml。

之后：两管加入稀盐酸 → 混匀 → 加入 25% 氯化钡溶液 → 加水至 50ml → 充分混匀 → 暗处放置 → 黑色背景自上而下观察比较浑浊程度。

正确实验条件下：供试管浑浊浅于对照管，判断检查合格。

## 二十二、错误操作

不要简单禁止用户错误操作。

用户应该能够犯错，例如：拿错量筒、加入错误试剂、加入错误容器、加入过多/过少、液体倒洒、称量过量/不足、吸液过量/不足、混匀不足、观察方式错误。

Simulation Engine 先真实执行用户行为，Experiment Rule Engine 再判断这个行为是否符合实验规范。

需要区分 Simulation Result 和 Teaching Evaluation。

教学模式：错误时及时提示。
考核模式：不中断实验，后台记录所有错误，最后统一评分。

## 二十三、一键清台

支持文档中的“一键清台”。

一键清台只把暂时不用的仪器放回存储区域，不能错误删除实验数据、已经加入容器中的液体、实验历史。

应设计 `resetWorkspace()` 和 `resetExperiment()` 两个不同操作。

## 二十四、数据模型

Simulation State 至少包含：objects / containers / liquids / substances / reactions / spills / balance / pipettes / experiment / interaction / history。

所有用户操作记录 Event，便于实验回放、评分、错误分析和教学数据分析。

## 二十五、事件驱动

用户操作不要直接到处修改 Zustand。

设计统一 Simulation Event，例如：PICK_OBJECT / DROP_OBJECT / TARE_BALANCE / ADD_POWDER / START_POUR / LIQUID_TRANSFER / SPILL_LIQUID / INSERT_PIPETTE / ASPIRATE / DISPENSE / MIX_CONTAINER / START_REST / OBSERVE_RESULT。

统一经过 Interaction → Simulation Event → Physics / Simulation Engine → State Update → Rendering。

## 二十六、性能要求

目标：普通现代电脑 Chrome / Edge 浏览器稳定运行，优先保证约 60FPS 的交互体验。

合理使用 GLB / Draco / KTX2 / Instancing / LOD / Texture Compression。

不要因为“真实”直接引入极重的实时 SPH 流体系统导致浏览器无法运行。

物理真实性重点放在：体积守恒、液面方向、倾倒条件、流量、碰撞、落点、操作姿态、实际测量、反应结果，而不是模拟每一个水分子。

## 二十八、开发策略

第一阶段先完成“仿真核心 PoC”。

只需要：实验操作台、50ml 量筒、纳氏比色管、水。

实现完整链路：拿起量筒 → 自由移动 → 松开落到桌面 → 重新拿起 → 倾斜 → 液面保持水平 → 超过临界角开始倒水 → 流速随倾斜变化 → 水真实减少 → 液流真实落下 → 命中比色管后体积增加 → 没命中则洒到实验台 → 停止倾倒后液流停止 → 体积守恒。

PoC 没做好之前不要继续开发完整实验。

PoC 成功后增加天平、称量纸、葡萄糖、药勺、粉末，完成称量系统。

然后增加洗瓶、量筒、比色管，完成加水 / 转移。

然后增加刻度吸管、洗耳球、容量瓶，完成吸液。

## 三十、第三阶段

## 三十四、最终目标

我要得到的不是“一个看起来像化学实验的网页”，而是“一个运行在浏览器中的 Web 3D 实验仿真系统”。

必须满足：可自由操作、可犯错、有真实物理状态、有真实实验状态、数据连续变化、实验结果由用户实际操作决定、操作和结果具有因果关系、可以教学、可以考核、可以扩展其他实验。

所有技术决策优先围绕这个目标。

如果某个设计视觉上很好看但实际上只是预设动画，需要明确指出并避免。

如果真正物理模拟成本极高，不要偷偷降级；请明确说明真实模拟方案、近似模拟方案、性能成本、开发成本和两者差异，再由需求方决定。
